# YM2151 ノイズ発生器の調査

YM2151 のノイズ発生器は `NFRQ`（レジスタ `0x0F` の下位 5bit）で速さを変えられるが、
データシートに数値表が無い。[test/lfo_noise/](../lfo_noise/README.md) は LFO 経由でこれを
測っており、`P_n = (32 - NFRQ) / 2` [samples] という式を得ているが、**直接測れたのは
`NFRQ <= 0x0f` まで**で、上半分はその外挿だった（[§5.4.3](../lfo_noise/README.md#543-この測り方の限界)）。

ここでは NE（`0x0F` の bit7）でノイズを LFO に通さず**直接 DAC へ出し**、
`NFRQ` 全 32 値と、ノイズ発生器そのものの性質を測る。

## 1. 解析結果の要約

| 項目 | 結論 | 根拠 |
| --- | --- | --- |
| `NFRQ` とノイズ発生器の更新周期の関係 | 更新周期 = `(32 - NFRQ) / 2` samples。`NFRQ=0x00`〜`0x1e` の **31 値すべてを直接実測**（実測/予測 0.999〜1.001） | [§3](#3-結論の根拠) `[N]` |
| NE を立てたときの DAC 出力の形 | 一定の振幅に**ノイズ発生器のビットで符号を付けた 2 値**。符号は 1 サンプルに 1 回だけ変わりうる | [§3](#3-結論の根拠) `[N]`（連長が更新周期の整数倍に乗る割合が 32 条件すべてで 100.0%） |
| ノイズ発生器の系列の長さ | **131071 = 2^17 - 1 ステップ**で一巡する | [§3](#3-結論の根拠) `[O]`（32 条件すべてで一致率 100.0%） |

## 2. 判明した仕様

### 2.1 更新周期は `NFRQ` だけで決まる

    更新周期 P_n = (32 - NFRQ) / 2  [samples]

fs = 62500Hz（φM / 64）。φM で書けば `32 × (32 - NFRQ)` サイクル。
`NFRQ=0x00` で 16 サンプル（3906.25Hz）、`0x1e` で 1 サンプル（62.5kHz）。

**`NFRQ=0x00` から `0x1e` までの 31 値を 1 つ飛ばさず実測してある。**
[test/lfo_noise/](../lfo_noise/README.md) が LFO 経由で得た式と同じものだが、あちらは
`0x0f` までしか直接測れていない。`0x1f`（`P_n` = 0.5）だけはこの測定系でも届かない
（[§7](#7-不明点未解決事項)）。

### 2.2 NE の出力は符号だけが動く 2 値

NE を立てると、チャネル 7 の C2 の出力が**一定の振幅にノイズ発生器のビットで符号を
付けたもの**に差し替わる。DAC に出るのは 2 値だけで、実測では `+2040` と `-2044` の
2 種類しか現れない。

符号が変わりうるのは**ノイズ発生器が新しい語を出した瞬間だけ**で、しかも
**1 サンプルに 1 回しかラッチされない**。したがって L チャネルの符号列が
そのままノイズ発生器のビット列になる。

これは実測で裏づけてある。同じ符号が続く長さは、**32 条件すべてで 100.0% が
更新周期の整数倍**に乗る（[§5.1](#51-nfrq-全-32-値)）。符号が動きうる瞬間が更新周期おきにしか
来ていないということで、変化率から求めた `P_n` とは別経路の確認になる。

### 2.3 系列は 131071 ステップで一巡する

ノイズ発生器が出すビット列は **131071 = 2^17 - 1 ステップ**で完全に繰り返す。
`NFRQ` 全 32 値で同じ値になり、一致率はいずれも 100.0%（[§5.2](#52-系列の周期)）。

時間に直すと `NFRQ` で変わる。`NFRQ=0x00` なら 131071 × 16 サンプル = 33.5 秒、
`0x1e` なら 131071 サンプル = 2.1 秒。

### 2.4 ビット列は 17 段・タップ 14 と 17 の LFSR そのもの

出るビット列 `y` は次の漸化式を満たす。

    y[n] = y[n-14] ^ y[n-17]

**`NFRQ` 全 32 値・合計 2000 万ビット超で、外れが 1 ビットも無い**（[§5.3](#53-系列を作る漸化式)）。
タップ位置を当てて確かめたのではなく、**列そのものから最短の線形漸化式を求めて
17 段・タップ 14/17 が出てくる**（[§3](#3-結論の根拠) `[Q]`）。

対応する多項式 `x^17 + x^14 + 1` は**原始多項式**である。周期が 2^17 - 1 = 131071
（[§2.3](#23-系列は-131071-ステップで一巡する)）で、これは素数（メルセンヌ素数）なので、17 次の多項式が
この周期を持つならその位数は 2^17 - 1 しかありえない。全 0 以外のどの状態から
始めても 131071 個の状態を一巡する。

C で書くとこれだけになる。

```c
#include <stdint.h>

/* YM2151 のノイズ発生器。1 呼び出しで 1 ステップ進み、そのビットを返す。
   17bit のうち bit0 が最新。全 0 以外なら初期値は何でもよく、
   系列上のどこから始まるかが変わるだけ。 */
static uint32_t noise_lfsr = 1;

static int opm_noise_step(void)
{
    /* y[n] = y[n-14] ^ y[n-17] */
    uint32_t bit = ((noise_lfsr >> 13) ^ (noise_lfsr >> 16)) & 1;
    noise_lfsr = ((noise_lfsr << 1) | bit) & 0x1ffff;
    return (int)bit;
}
```

この実装が実機の列を再現することは 1 ビットずつ突き合わせて確かめてある。
**実測の先頭 17 ビットだけを初期値に詰めて生成すると、残り全部が一致する**
（32 条件すべてで不一致 0、最長 250 万ビット。[§5.3](#53-系列を作る漸化式)）。

出力までを含めるとこうなる。更新の刻みはサンプルの半分を単位に数える
（[§2.1](#21-更新周期は-nfrq-だけで決まる) の `P_n` が 0.5 刻みの値を取ることがそのまま根拠になる）。

```c
/* NE=1 のときのチャネル 7 C2 の出力。level はそのオペレータの EG のレベル。
   1 サンプル = 2 刻み。ノイズは (32 - nfrq) 刻みごとに 1 ステップ進む。 */
static int32_t opm_noise_out(uint8_t nfrq, int32_t level)
{
    static uint32_t tick;
    static int bit;

    for (int i = 0; i < 2; i++)             /* 1 サンプルぶん = 2 刻み */
        if (++tick >= (uint32_t)(32 - (nfrq & 0x1f))) {
            tick = 0;
            bit = opm_noise_step();
        }
    return bit ? -level : level;            /* 1 で負、0 で正 */
}
```

符号の向き（`y` が 1 のとき DAC の低い側）も実測で決まっている。この向きでのみ
上の 2 タップの漸化式が成り立ち、反転させると成り立たない（[§5.3](#53-系列を作る漸化式)）。

**決まっているのは「外から見える系列」であって、チップ内部のレジスタ幅や配線ではない。**
同じ系列を出す回路は他にもありうる（たとえば 16bit のレジスタを回しながら
帰還を間欠的に有効にする作りでも、時間方向に展開すれば同じ漸化式になる）。
`nfrq = 0x1f` のときの `32 - nfrq = 1` 刻み（= 1 サンプルに 2 回）は測れていない
（[§7](#7-不明点未解決事項)）。

## 3. 結論の根拠

数値はすべて [analyze_noise.py](analyze_noise.py) の出力で、`result/summary_wav_ne.txt` に置いてある。

| 主張 | 根拠（集計の節） | 数値 | 詳細 |
| --- | --- | --- | --- |
| 更新周期は `(32 - NFRQ) / 2` samples | `[N]` 符号の変化率から求めた `P_n` | `NFRQ=0x00`〜`0x1e` の 31 値で**実測/予測 0.999〜1.001** | [§5.1](#51-nfrq-全-32-値) |
| 符号が動くのは更新の瞬間だけ | `[N]` 連長が `P_n` の整数倍に乗る割合 | **32 条件すべてで 100.0%** | [§5.1](#51-nfrq-全-32-値) |
| 系列は 131071 ステップで一巡する | `[O]` ずらした列との一致 | **32 条件すべてで 131071 / 一致率 100.0%** | [§5.2](#52-系列の周期) |
| 漸化式は `y[n] = y[n-14] ^ y[n-17]` | `[Q]` 列から同定した最短の線形漸化式 | 32 条件すべてで**段数 17 / タップ 14,17**、全長での不成立 **0** | [§5.3](#53-系列を作る漸化式) |
| 17 段 LFSR の実装が実機の列を再現する | `[Q]` 先頭 17 ビットを種にした生成列との突き合わせ | 32 条件すべてで不一致 **0**（最長 250 万ビット） | [§5.3](#53-系列を作る漸化式) |
| `NFRQ=0x1f` はこの測定系では決まらない | `[P]` 基準列の間引き方を変えた突き合わせ | 1 個おき / 2 個おきの**どちらでも 100.00% 一致する** | [§7](#7-不明点未解決事項) |

`[N]` の 2 行は別経路である点が要点。1 行目は「隣り合うサンプルで符号が変わった割合」
という統計量から、2 行目は「同じ符号が何サンプル続いたか」という長さの分布から出ており、
片方が合っていても他方が外れることはありうる。両方が全条件で揃っている。

## 4. 解析方法

### 4.1 なぜ LFO 経由と別に測るのか

[test/lfo_noise/](../lfo_noise/README.md) は LFO の値からノイズ語の供給周期 `P_n` を測っている。
そちらで分かっているのは次の 2 点。

- `P_n = (32 - NFRQ) / 2` [samples]（[§2.2](../lfo_noise/README.md#22-lfo-値が変わる間隔はノイズ語の更新周期との合成で決まる)）
- ただし**直接測れたのは `NFRQ <= 0x0f` まで**。LFO のラッチ格子が最短 8 サンプルなので、
  `P_n` がそれを下回る側は「毎段が新しい語」に飽和して速さを区別できない
  （[§5.4.3](../lfo_noise/README.md#543-この測り方の限界)）。**式の上半分は外挿だった**

NE (`0x0F` の bit7) を立てるとノイズがチャネル 7 の C2 の出力に直接差し替わる。
LFO を経由しないので**格子が DAC の 1 サンプルになり、8 倍細かく測れる**。

### 4.2 測定系

- ターゲット: Raspberry Pi Pico 2 + YM2151、φM = 4.000000MHz（`OPM_CLOCK_MODE_4MHZ`）
- OPM の内部サンプルレート fs = φM / 64 = **62500Hz**
- ロジアナ: fx2lafw、8MHz サンプリング。WAV は 62500Hz / 16bit / stereo
- **解析に使うのは L (CH1) だけ**（[../dac_lr/README.md](../dac_lr/README.md)）

`opm_noise_seq.txt` が実機に流し込む設定の要点:

- `0x0F` に **NE=1 + NFRQ**。プレースホルダ `@NFRQ@` には bit7 を含めた値
  （`0x80 | NFRQ`）を渡す。ファイル名の `nfrq_` もこの値になる
- ノイズが差し替わるのは**チャネル 7 の C2** なので、レジスタは ch0 の並び
  (`0x40`/`0x50`/`0x48`/`0x58`) に `+7` した番地を使う。KON は `w 08 7f`
- ch7 は `ALG=7`（4 op すべてキャリア）。**C2 だけ `TL=0`、他の 3 個は `TL=127`** で
  黙らせるので、出力は C2 = ノイズだけになる
- 各オペレータ: `AR=31` / `D1R=0` / `D2R=0` / `D1L=0` / `RR=15`
- **LFO は使わない**（`LFRQ=0` / `AMD=PMD=0` / `PMS=AMS=0` / `W=0`）
- キャプチャの前後をハードウェアリセット (`r`) で挟む

### 4.3 出力の性質と測り方

NE の出力は **EG のレベルにノイズ発生器のビットで符号を付けた 2 値**で、符号は
1 サンプルに 1 回ラッチされる。したがって **L の符号列がノイズ発生器のビット列そのもの**になる。
これが測り方の全部を決める。

**更新周期 `P_n`.** 符号が変わりうるのは新しい語が出た瞬間だけで、そのとき 1/2 の確率で
反転する。隣り合うサンプルで符号が変わった割合を `r` とすると

    P_n = 0.5 / r  [samples]

`P_n` が 1 サンプルを下回ると 1 サンプルに複数回更新が入るので `r` は 0.5 で頭打ちになる。
**測れるのは `P_n >= 1`、すなわち `NFRQ <= 0x1e` まで。**

**独立な点検.** 符号が変わりうるのが更新の瞬間だけなら、**同じ符号が続く長さは必ず
`P_n` の整数倍**になる。これは変化率とは別の情報なので、推定が当たっているかの
点検に使える（許容は 1 サンプル。更新の瞬間は `P_n` おきに来るがサンプルは整数位置に
しか無いので、`P_n` が半端な値のとき連長は 1 サンプルまでずれる）。

**系列の周期.** 連長を `P_n` で割ると 1 ステップ 1 ビットの列に戻せる。この列の
先頭 64 ステップのパターンが次に現れる位置を 1 パスで探し、そこから先が全部一致するかを
確かめる。遅れを総当たりすると 10 万ステップ級の周期には現実的な時間で届かない。

**`k * P_n` の位置を直接拾ってステップ列を作ってはいけない。** `P_n` の推定には
わずかな誤差があり、10 万ステップも進むと数十ステップぶんずれて周期が見つからなくなる。
連長から積み上げれば誤差が溜まらない。

### 4.4 データセット

| ディレクトリ | 条件数 | 用途 |
| --- | --- | --- |
| `wav_ne/` | 32 | `NFRQ` 全 32 値 × 40 秒。`NFRQ=0x00` でも系列 1 周（131071 ステップ = 33.5 秒）が収まる長さ |

キャプチャは [test/lfo_noise/capture_lfo.py](../lfo_noise/capture_lfo.py) を `--seq` で流用する。
`opm_noise_seq.txt` が使うプレースホルダは `@NFRQ@` と `@TIME@` だけで、
`opm-writer.py` は**使わなかった `-D` をエラーにしない**（未定義の `@KEY@` だけを弾く）ので
そのまま通る。`--min-ms` と `--max-ms` を同じ値にしてキャプチャ長を固定する。

```bash
NF=$(python3 -c "print(','.join('%02x'%(0x80|i) for i in range(32)))")
../lfo_noise/capture_lfo.py --seq ./opm_noise_seq.txt --wav-dir ./wav_ne --mode am \
  --lfrq-start 00 --lfrq-end 00 --min-ms 40000 --max-ms 40000 --nfrq "$NF"

# 長さの検査（--min-ms / --max-ms を同じ値で渡す）
../lfo_noise/capture_lfo.py --wav-dir ./wav_ne --check --min-ms 40000 --max-ms 40000
```

`--mode am` は 1 本だけ回すための指定で、AM 測定という意味は無い（このシーケンスは
`@PMD@` などのモード依存の値を一切使わない）。ファイル名に入る `lfrq_00` も同じく無意味。

### 4.5 解析と集計の手順

```bash
./analyze_noise.py              # wav_ne/ を全部解析して [N] を出す
./analyze_noise.py --period     # [O] 系列の周期も探す
./analyze_noise.py --self-test  # 人工信号で検証する（実機不要）
```

| `result/` の中身 | 内容 |
| --- | --- |
| `summary_wav_ne.txt` | `[N]` 更新周期 / `[O]` 系列の周期 / `[Q]` 漸化式 / `[P]` 間引きの区別が付かないこと |

**この解析器は人工信号で検証してある**（実機不要、全ケース PASS で終了コード 0）。
既知の更新周期（16 / 15.5 / 8 / 4 / 2 / 1 サンプル）を入れて戻るか、`P_n` = 0.5 で
飽和するか、ステップ列の復元が元の列に戻るか、既知の周期で繰り返す列からその周期を
見つけられるか、周期の無い列では見つけないかを確かめている。
漸化式の同定については、**既知のタップで作った列からそのタップを言い当てられるか**を
2 通りのタップで確かめ、17 段 / タップ 14,17 の周期が 2^17 - 1 になること、
先頭 17 ビットを種にすると続きを再現できることも見ている。

  測った値（実測/予測 0.99〜1.02）と一致する。**LFO に供給される語と NE で出るビットが
  同じ発生器から来ていることの実測**になる

### 5.3 系列を作る漸化式

根拠は `result/summary_wav_ne.txt` の `[Q]`。**タップ位置を仮定しない**。
先頭 512 ステップに Berlekamp-Massey を掛けて最短の線形漸化式を求め、
出てきた漸化式が全長で成り立つかを見る。

| NFRQ | steps | 同定した段数 | 同定したタップ | 漸化式の不成立 | 生成列との不一致 |
| --- | --- | --- | --- | --- | --- |
| `00` | 156228 | 17 | 14, 17 | 0 | 0 |
| `08` | 208302 | 17 | 14, 17 | 0 | 0 |
| `10` | 312452 | 17 | 14, 17 | 0 | 0 |
| `18` | 624906 | 17 | 14, 17 | 0 | 0 |
| `1e` | 2499621 | 17 | 14, 17 | 0 | 0 |
| `1f` | 2499621 | 17 | 14, 17 | 0 | 0 |

（全 32 行は `result/summary_wav_ne.txt`。**32 条件すべてが同じ結果**で、
合計は 2000 万ビットを超える）

- **段数もタップも列から出てくる。** 当てて確かめたのではないので、
  他のタップの組では説明できないことも同時に示している
- **生成列との不一致 0** は、[§2.4](#24-ビット列は-17-段タップ-14-と-17-の-lfsr-そのもの) の C 実装が実機の出力を
  1 ビットも違わず再現するということ。実測の先頭 17 ビットだけを初期値に詰め、
  そこから先は一切実測を参照せずに生成している
- **極性も決まっている。** DAC の高い側を 0 に取ると 2 タップの漸化式になり、
  反転させると成り立たない。反転した列に同じ手続きを掛けると段数 18 になり、
  タップは 1, 14, 15, 17, 18 の 5 本になる（`(1 + x)(1 + x^14 + x^17)` に相当）

**間引き方は結果を変えない。** 観測しているのは物理的なシフト列を 2 の冪で
間引いたものだが（[§7](#7-不明点未解決事項) の `[P]`）、この間引きは最小多項式を変えない。
実際、`NFRQ` を `0x00` から `0x1f` まで変えると 1 ステップあたりの実時間は 32 倍
変わるのに、同定される漸化式は 32 条件すべてで同じである。

## 6. 考察

**[test/lfo_noise/](../lfo_noise/README.md) の `(32 - NFRQ)/2` は外挿ではなくなった。**
あちらは LFO のラッチ格子（最短 8 サンプル）が下限になるため `NFRQ <= 0x0f` までしか
直接測れていなかったが、NE で直接出せば格子が 1 サンプルになり、`0x1e` まで届く。
重なる範囲（`0x00`〜`0x0c`）で両者が一致するので、**2 つの経路が同じ発生器を見ている**
ことも確かめられた。

**測り方が桁違いに素直になった。**LFO 経由では搬送波の選び方・段ごとのゲイン推定・
飽和の補正といった手当てが要り、飽和側では系統的な偏り（PM で 1.06 倍、AM で 1.41 倍）が
残っていた（[§5.4.3](../lfo_noise/README.md#543-この測り方の限界)）。NE 経由の出力は 2 値なので、
符号を数えるだけで済み、32 条件すべてで 0.1% 以内に収まる。

## 7. 不明点・未解決事項

- **`NFRQ=0x1f` の `P_n` はこの測定系では決まらない。** 予測は 0.5 サンプルで、
  1 サンプルに 2 回更新が入ることになるが、DAC は 1 サンプルに 1 回しか値を出さないので
  変化率 `r` は 0.5 で頭打ちになる（`0x1e` と区別が付かない）。

  **ビット列そのものからも決められない。**「1 サンプルに 2 回進んでいるなら、観測列は
  基準列を 1 個おきではなく 2 個おきに間引いたものと一致するはず」という切り分けを
  試したが、`[P]` のとおり**どちらでも 100.00% 一致する**。系列は 2 の冪で間引いても
  自分自身の巡回シフトになるため、間引き方の違いが観測列に現れない。
  `0x1e` でも `0x1f` でも同じ結果になる。
- **リセット直後にノイズ発生器がどの状態から走り出すかは測っていない。**
  本データセットは `NFRQ` 1 値につき 1 本しか撮っていないので、同じ条件を撮り直したときに
  同じ位置から始まるかを比べられない。

## 8. 今後の課題

- **`NFRQ=0x1f` を決める**: [§7](#7-不明点未解決事項) のとおり、DAC 出力を 1 サンプル単位で見ている限り
  `0x1e` と区別が付かない。区別するには**サンプルより細かい時間分解能を持つ観測量**が要る。
  この測定系で唯一それを持つのはロジックアナライザが直接見ている SO / SH1 / SH2 の
  シリアル出力そのもの（8MHz サンプリング = 1 サンプルあたり 128 点）だが、
  そこに現れるのは DAC に出た後の値なので、1 サンプル内で 2 回起きた更新は残らない。
  **チップの外側からは原理的に届かない**可能性が高く、そう判断するにはもう 1 段の
  切り分けが要る。
- **リセット後の初期状態を測る**: 同じ `NFRQ` を 3 本ずつ撮り、ステップ列の先頭 64 ビットが
  同じ位置から始まるかを見る。`[P]` で使っている位置合わせがそのまま使えるので、
  解析器の追加は要らない。1 本 40 秒なので `NFRQ` 2 値 × 3 本で 4 分。
  揃うなら「リセットで初期化され決定的に走る」ことの直接の実測になり、揃わないなら
  キャプチャ開始位置の揺れの大きさが測れる。
  [test/lfo_noise/ の §5.6](../lfo_noise/README.md#56-段ごとの値列を突き合わせる) で LFO 経由の値列に見えた
  「揃う組と揃わない組がある」という現象を、LFO を挟まずに切り分けられる。

## 付録 A. レジスタの割り当て

`opm_noise_seq.txt` が書くチャネル 7 のレジスタ。オペレータのレジスタは
`ベース + スロット * 8 + チャネル` で、スロットの並びは M1 / M2 / C1 / C2。

| | M1 | M2 | C1 | **C2（ノイズ）** |
| --- | --- | --- | --- | --- |
| DT1 / MUL | `0x47` | `0x4f` | `0x57` | **`0x5f`** |
| TL | `0x67` | `0x6f` | `0x77` | **`0x7f`** |
| KS / AR | `0x87` | `0x8f` | `0x97` | **`0x9f`** |
| AMS-EN / D1R | `0xa7` | `0xaf` | `0xb7` | **`0xbf`** |
| DT2 / D2R | `0xc7` | `0xcf` | `0xd7` | **`0xdf`** |
| D1L / RR | `0xe7` | `0xef` | `0xf7` | **`0xff`** |

チャネル単位のレジスタは `0x27`（RL / FB / CONNECT）、`0x2f`（KC）、`0x30`（KF）、
`0x3f`（PMS / AMS）。KON は `0x08` に `0x7f`（全スロット + チャネル 7）。
