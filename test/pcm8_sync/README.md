# FM と ADPCM の発音タイミングのずれ

FM（YM2151 → YM3012 → PIO キャプチャ）と ADPCM（[pcm8.c](../../pcm8.c) のソフトデコード）は
`ym3012_reader_read_pcm()` の中でフレーム番号を突き合わせて足され、I2S と USB CDC #1 へ出る。
MDX が両者を**同じ tick でキーオン**したとき、出力の中で立ち上がりが揃うかを実測した。

対象は I2S と USB キャプチャだけ。**YM3012 のアナログ出力には ADPCM が乗らない**ので、
そちらを聴いている限りこのずれは存在しない。

数値はすべて φM 4MHz（出力 62500 フレーム/s、**1 フレーム = 16µs**）のもの。

## 1. 解析結果の要約

| 項目 | 結論 | 根拠 |
| --- | --- | --- |
| 修正前の FM と ADPCM の発音時刻の関係 | **ADPCM が先行する。**実曲で最大 126 フレーム = 2.0ms。1 音ごとに値が変わる揺らぎで、固定オフセットではない | [§3.1](#31-修正前adpcm-が-fm-より先に出る) |
| 先行量を決めているもの | `pcm8_service()` のレンダリング前線 `s_rendered_total` が「今」より後ろにある量そのもの。束ね（`PCM8_BATCH_FRAMES` = 64 フレーム）と音声チェーンの間引き（`AUDIO_SERVICE_INTERVAL_US` = 500µs = 31 フレーム）の噛み合わせで決まる | [§3.2](#32-先行量はレンダリング前線の遅れそのもの) |
| ADPCM が発音中かどうかによる違い | 無音からの発音は間引きぶんだけ（10〜39 フレーム）、発音中の追加発音には束ねも乗る（14〜101 フレーム） | [§3.3](#33-束ねが効くのは発音中だけ) |
| 修正後に残るずれ | 0〜3 フレーム = 0〜48µs。機構由来の成分は 0 | [§3.4](#34-修正後は機構由来の成分が-0-になる) |

## 2. 判明した仕様

### 2.1 FM は実時刻に固定され、ADPCM は固定されていなかった

キャプチャリングのフレーム番号 N は実時刻 N/62500 に固定されている。DMA の書き込み位置と
`s_write_total` が `s_write_total ≡ 書き込み添字 (mod 4096)` で結ばれていて
（[ym3012.c](../../ym3012.c) の `ym3012_ring_poll()`）、途中で位相がずれない。したがって
`opm_write()` した瞬間の FM の音は、その瞬間のフレーム番号に入る。

ADPCM 側はフレーム番号を自分で選ぶ。`pcm8_service()` が描くのは

    [s_rendered_total, ym3012_write_total())

という **「今」より過去に向かう**区間なので、キーオンした音はその時点の
`s_rendered_total` = **過去のフレーム番号**から鳴り始めていた。

### 2.2 束ねと間引きは、そのまま発音時刻の誤差になっていた

`s_rendered_total` の遅れを決めるのは次の 2 つ。どちらも CPU の固定費を下げるための
仕組みで、音質のための設計ではない。

| 仕組み | 値 | 効き方 |
| --- | --- | --- |
| `PCM8_BATCH_FRAMES`（[pcm8.c](../../pcm8.c)） | 64 フレーム | **発音中だけ**、64 フレーム溜まるまで描かない |
| `AUDIO_SERVICE_INTERVAL_US`（[pico-opm-writer.c](../../pico-opm-writer.c)） | 500µs = 31 フレーム | リング位置の取り込みと描画を 500µs ごとにまとめる |

31 フレームずつ進む `w` に対して束ねの閾値が 64 なので、発音中は 3 回に 1 回しか描かない。
前線の遅れは 0〜93 フレームを往復し、そこへメインループが長く止まった回が加わる。

### 2.3 実機 X68000 とは向きも逆だった

MXDRV は FM のレジスタを書いてから ADPCM を叩く。[mdx.c](../../mdx.c) の tick ループも
チャンネル番号順（FM 0-7 → ADPCM 8-15）に処理するので、**キーオンの発行順は FM が先**。
実機では ADPCM がわずかに遅れるはずのところ、pcm8 が過去へ描くせいで先行に転じていた。

### 2.4 直し方

**発音状態を変える前に、その瞬間のフレーム番号まで描き切る。**
[pcm8.c](../../pcm8.c) の `flush_now()` がこれを行い、`pcm8_key_on()` /
`pcm8_stop()` / `pcm8_set_mode()` / `pcm8_abort_all()` / `pcm8_iocs_out()` /
`pcm8_iocs_mod()` / `pcm8_set_enabled()` の入口から呼ばれる
（`pcm8_close_pdx()` は `pcm8_abort_all()` 経由）。

**`ym3012_ring_poll()` をその場で呼ぶのが肝。** 呼ばないと `ym3012_write_total()` は直前の
音声チェーン（最大 500µs 前）の値のままで、間引きぶんの 31 フレームが残る。

束ねそのものは撤去していない。発音状態が変わらない区間では時刻の誤差を生まないため。

## 3. 結論の根拠

測定は 2 系統ある。**波形から測ったもの**（出力に本当にそう出ているか）と、
**ファーム内部のカウンタ**（機構がそう動いているか）で、独立に同じ量を指す。

### 3.1 修正前、ADPCM が FM より先に出る

FM を右、ADPCM を左に振り分けた [SYNC.MDX](gen_testdata.py) を鳴らして 8 秒取り込み、
左右それぞれの立ち上がりフレームを比べた（[§4](#4-解析方法)）。**正が「ADPCM のほうが早い」。**

| 条件 | 対の数 | min | max | 幅 | 平均 | 平均 (µs) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| quiet（音の合間は ADPCM が 1ch も鳴っていない） | 326 | 10 | 39 | 29 | 18.36 | 293.7 |
| busy（ほぼ無音のドローンで発音中を保つ） | 326 | 14 | 101 | 87 | 47.22 | 755.5 |

実曲（`DRACULA/dra03.mdx` を 60 秒）では内部カウンタで **min 1 / max 126 / 平均 32 フレーム**、
すなわち**最大 2.0ms** に達した。合成した曲より大きいのは、PDX の読み出しや音色の展開で
メインループが長く止まる回があるため。

### 3.2 先行量はレンダリング前線の遅れそのもの

キーオンの瞬間に `ym3012_write_total() - s_rendered_total` を数える診断を当てて
（[diag.patch](diag.patch)）、同じ 8 秒のあいだ同時に記録した。

| 条件 | 波形から (min/max/平均) | 内部カウンタ (min/max/平均) |
| --- | --- | --- |
| quiet | 10 / 39 / 18.4 | 7 / 37 / 16 |
| busy | 14 / 101 / 47.2 | 6 / 100 / 44 |

**2 つは 2〜3 フレーム以内で一致する。** 差は FM 側だけに掛かる分（キャプチャ経路の
1 フレームと、正弦波が検出閾値を跨ぐまでの 1 フレーム）と、tick 内で FM のキーオンが
先に出る分が相殺した残り。前線の遅れ以外に、ずれを作っている要素は無い。

### 3.3 束ねが効くのは発音中だけ

quiet と busy の違いはドローン 1 本の有無だけで、測定対象の 2 チャンネルは同一。それでも

- quiet の幅 29 フレーム ≈ 間引きの 31 フレーム
- busy の幅 87 フレーム ≈ 間引き 31 + 束ね 64 = 95 フレーム

となり、`pcm8_service()` の `s_sounding && behind < PCM8_BATCH_FRAMES` という条件
（発音中だけ束ねる）がそのまま分布の幅に出ている。

### 3.4 修正後は機構由来の成分が 0 になる

同じ測定を修正後に繰り返した。

| 条件 | 対の数 | min | max | 幅 | 平均 | 平均 (µs) | 内部カウンタ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| quiet | 326 | 1 | 3 | 2 | 2.02 | 32.4 | 0 / 1 / 0 |
| busy | 326 | 0 | 2 | 2 | 1.52 | 24.2 | 0 / 1 / 0 |
| 実曲 (60 秒) | — | — | — | — | — | — | 0 / 1 / 0 |

内部カウンタが全条件で 0〜1 フレームということは、**ADPCM がキーオンした瞬間の
フレーム番号から鳴り始めている**ということ。残った 0〜3 フレームは FM 側と検出側の
バイアスで、[§3.2](#32-先行量はレンダリング前線の遅れそのもの) で見た 2〜3 フレームと同じもの。

### 3.5 退行が無いこと

`DRACULA/dra03.mdx` を 60 秒、同じ条件で修正前後に鳴らして比べた。

| 指標 | 修正前 | 修正後 |
| --- | --- | --- |
| `I2S` UNDERRUN | 0 | 0 |
| `I2S` MIN（先行量の谷） | 843 | 843 |
| `OVERRUN` / `E0` / `RXSTALL` | 0 | 0 |
| `MDX PCM` keyon / miss / reads | 341 / 0 / 595 | 341 / 0 / 595 |
| `CLIP` | 0 | 2 |
| `SEQ LAG` max | 84 µs | 90 µs |
| `CPU` | 39% | 39% |
| `SVCTIME` pcm8 + mdx | 17815 + 33979 = 51794 µs/s | 17648 + 32307 = 49955 µs/s |

**発音の判定は 1 回も変わっていない**（keyon / miss / reads が完全に一致）。描く総量も
変わらないので `SVCTIME` の合計も増えていない（差の 3.5% は実行ごとのばらつきの範囲）。
`CLIP` の 2 は、ブロックの切れ目が動いたことで飽和の判定が数フレームずれたもの。

`t` の自己テストは `pcm PASS` / `mdx PASS (7 pitch, 5 tempo)` / `adpcm PASS (19 cases)`。

## 4. 解析方法

### 4.1 左右に振り分けて 1 回のキャプチャで比べる

FM と ADPCM が同じ tick でキーオンするだけの曲を作り、**FM を右・ADPCM を左**に置く。
差分も相互相関も要らず、同じキャプチャの中で立ち上がりを直接比べられる。

- FM は OPM の `0x20+ch` の `RL` で片側だけに出す。反対側のスロットには何も加算されない。
- ADPCM は [pcm8.c](../../pcm8.c) の `render_block()` が `pan & 1` で L、`pan & 2` で R に
  振り分ける。ミックスリングの段階で片側は 0 のまま。**PCM8 の定位は全チャネル共通**なので、
  鳴らすチャンネルはすべて `p1` にしてある。

左右の DAC スロットは同じ値にならない（[../dac_lr/](../dac_lr/README.md)）が、その差は
1 フレーム未満で、ここで測る 100 フレームには効かない。

### 4.2 立ち上がりを鋭くする

| 側 | 波形 | 立ち上がり |
| --- | --- | --- |
| ADPCM | 8bit PCM 形式（mode 6）の直流 0x60 | 1 ソースサンプル = 4 出力フレームで全振幅。実測では 1 フレームで 0 → 24576 |
| FM | 1 オペレータ（CON=7 で C2 だけ TL=0）、AR=31、音符 84（約 2.5kHz） | 実測で 0 → 2008 → 8144 の 3 フレーム |

ADPCM 形式（mode 0-4）を使うと、MSM6258 のステップ幅が 16 から始まるので全振幅まで 1ms
ほどかかり、測りたい量と同じ桁になってしまう。**そのため ADPCM 形式は使っていない。**
デコーダ自体の検証は `t` の `adpcm` が既知ベクタで行う。

### 4.3 2 条件を作る

`pcm8_service()` は `s_sounding`（直前の描画で発音していたか）が真のときだけ束ねる。
そこで 2 つ用意した。

| ファイル | 条件 | 中身 |
| --- | --- | --- |
| `SYNC.MDX` | quiet | FM ch0 と ADPCM ch8 だけ。音の合間は ADPCM が 1ch も鳴っていない |
| `SYNC2.MDX` | busy | 上に加えて ADPCM ch9 でドローンを鳴らし続ける |

ドローンは PDX のエントリ 1（振幅 1 の直流）を最小音量（`@v42` = PCM8 の音量 0 = 利得
0.158）で鳴らすもので、出力は 40 前後。解析の閾値 500 のはるか下なので立ち上がりの検出に
掛からない。ゲートタイムだけ `q8`（= 音の長さいっぱい）にして、キーオフと次のキーオンが
同じ tick に来るようにしてある。`q2` にすると 1/3 の時間しか鳴らず、束ねが働かない。

### 4.4 立ち上がりの決め方

無音が 64 フレーム続いたあと、最初に絶対値 500 を超えたフレームを立ち上がりとする。
無音区間は厳密に 0 になるので、閾値は雑音を跨ぐためではなく**アタックのごく初期の
1-2 フレームを無視するため**にある。

閾値のぶんの遅れは L / R それぞれで一定なので、**分布の幅**と**条件間の平均の差**には
効かない。この 2 つが結論に使っている量で、絶対値そのものは使っていない。

対応づけは「L の各立ち上がりに対し 768 フレーム以内で最も近い R」。片側が取りこぼされた
音は捨てる。8 秒で 326 対が取れ、これは音の間隔 24.58ms から期待される数と一致する。

検出器と対応づけは [analyze_sync.py](analyze_sync.py) の `--self-test` が 15 ケースで
検証する（実機不要）。生成物の書式は [gen_testdata.py](gen_testdata.py) の `--self-test` が
27 ケースで検証する。

### 4.5 内部カウンタ

波形の測定は FM 側のバイアスを含む。機構そのものを見るために、キーオンの瞬間に
`ym3012_ring_poll()` してから `ym3012_write_total() - s_rendered_total` を数える診断を
当てた。実装は [diag.patch](diag.patch)、使い方は[付録](#付録)。**本体には残していない。**

### 5.3 残差 1〜2 フレームの内訳

3 つの成分がある。いずれも 1 フレーム前後で、打ち消し合って正味 1〜2 フレームになる。

| 成分 | 量 | 向き |
| --- | --- | --- |
| 検出の閾値。FM は正弦波なので 0 を離れてから 500 を跨ぐまで 1 フレームかかる | +1 | ADPCM が早く見える |
| キャプチャ経路。FM の 1 サンプルは、OPM が計算した次のフレームでリングに入る | +1 前後 | ADPCM が早く見える |
| tick 内の順序。ch0（FM）のキーオンが ch8（ADPCM）より先に発行される | −1〜−2 | ADPCM が遅く出る |

3 番目が小さいのは、この曲では音色・音程・音量が毎回同じで**キーオンのたびに書くのが
`0x08` の 1 本だけ**だから。音色を展開し直す曲では 25 本になり、その分だけ ADPCM が
遅れる。これは参照実装と同じ挙動で、修正の対象ではない。

### 5.4 実曲での内部カウンタ

`DRACULA/dra03.mdx` を 60 秒（keyon 341 回）。

| | min | max | 平均 |
| --- | ---: | ---: | ---: |
| 修正前 | 1 | 126 | 32 |
| 修正後 | 0 | 1 | 0 |

修正前の max 126 は、合成した曲の 100 より大きい。束ね 64 + 間引き 31 = 95 を超えるのは、
PDX の読み出しや音色の展開でメインループが 1 回の音声チェーン間隔より長く止まった回が
あるため。**遅れの上限は 2 つの定数では決まらず、そのときのメインループの詰まり方で
決まっていた。**

## 6. 考察

### 6.1 聴こえるかどうかとは別に、直す価値がある

2.0ms は 2 つの音の同時性としては閾値以下で、これだけを理由に音の違いを聴き分けるのは
難しい。それでも直したのは次の理由による。

- **揺らぐ。** 固定オフセットなら「そういう音」で済むが、1 音ごとに 0〜2ms 動くので
  リズムパートでは打点が安定しない。
- **上限が決まらない。** [§5.4](#54-実曲での内部カウンタ) のとおり、メインループが
  詰まるほど大きくなる。機能を足していくと悪化する側の量だった。
- **向きが実機と逆だった。** MXDRV は FM を書いてから ADPCM を叩くので、実機では ADPCM が
  わずかに遅い。忠実さを目標にしている以上、符号が逆なのは直す理由になる。
- **直すコストがほぼ 0 だった。** ミックスリングがもともとフレーム番号で引く冪等な設計
  だったので、前線を実時刻へ寄せるだけで済み、描く総量も変わらない
  （[§3.5](#35-退行が無いこと)）。

### 6.2 「間引いてよいもの」と「間引いてはいけないもの」

メインループは各サービスを最短間隔を決めて回す。これは 1 周あたりの固定費を下げるための
設計で、**信号の流れ（1 秒に 62500 フレーム）に対しては透明**である。リングの読み書きは
フレーム番号で結ばれていて、いつ読みに行っても内容は同じだからである。

**透明でなくなるのは、間引いた側が新しい内容を書き込む瞬間だけ。** 今回の ADPCM の
キーオンがまさにそれで、「いつ描くか」は自由でも「どのフレーム番号から描くか」は自由に
できない。同じ構造は、外から時刻を持ち込む操作すべてに当てはまる。

### 6.3 束ねを外す選択肢を採らなかった理由

`PCM8_BATCH_FRAMES` を 1 にすれば束ねの成分は消えるが、間引きの 31 フレームは残るうえ、
ブロックの支度の固定費が 64 倍になる。`AUDIO_SERVICE_INTERVAL_US` を縮めれば間引きの
成分も減るが、こちらはメインループ全体の周回数に効く（[README §3.11.1](../../README.md#3111-サービスの呼び出し間隔)）。
どちらも**誤差を小さくするだけで 0 にはできず、CPU を確実に食う。**
発音の瞬間に前線を寄せる方法は誤差を 0 にして CPU を食わない。

## 7. 不明点・未解決事項

- **音色を展開し直す曲での FM 側の遅れを測っていない。**
  [§5.3](#53-残差-12-フレームの内訳) のとおり、キーオンごとに 25 レジスタを書く曲では
  FM のキーオンが 700µs 前後かかり、その分 ADPCM が遅れて出る。これは参照実装と同じ
  挙動なので修正の対象ではないが、**実際に何フレームになるかは測っていない。**
- **平均値が取り込み長に依存する。** [§5.1](#51-修正前の分布) のとおり、キーオンの位相が
  8 秒より長い周期でゆっくり動くため、1 回のキャプチャの平均は真の平均ではない。
  結論に使ったのは分布の幅と修正前後の差なので影響しないが、**修正前の「平均 47 フレーム」
  という値そのものは条件に依存する。**
- **`ym3012_ring_poll()` をキーオンのたびに呼ぶことの影響を切り分けていない。**
  [§3.5](#35-退行が無いこと) で `SVCTIME` の合計が増えないことは確かめたが、この呼び出し
  単体の費用は測っていない。DMA のレジスタ読み 1 回と加算数回なので無視できるはずだが、
  未確認。
- **8ch を同時に鳴らす曲での挙動を測っていない。** ドローン 1 本で束ねを働かせたが、
  8ch すべてが鳴っている状態では 1 回の描画量が増える。前線を寄せる操作がキーオンごとに
  走るので、tick の中での CPU の山は高くなるはず。`SEQ LAG` に出るかは未確認。

## 8. 今後の課題

- **音色展開を伴うキーオンでの FM 側の遅れを測る。** [gen_testdata.py](gen_testdata.py) の
  FM チャンネルに、音符ごとに `@`（`0xFD`）を挟むだけでよい。音色は同じものを指しても
  `F17_VOICE_REQ` が立つので 25 レジスタが毎回書かれる。同じ測り方で L と R の差を取れば、
  参照実装どおりの遅れが何フレームなのかが出る。実機での同時性の上限を知る意味がある。
- **位相の偏りを消して真の平均を出す。** 音の間隔を音声チェーンの間引き（500µs）と
  互いに素な値にすれば、短い取り込みでも位相が一巡する。`NOTE_CLOCKS` と `TEMPO` を
  選び直して、たとえば 1 音 25.1ms（= 500µs の整数倍から少しずらす）にすればよい。
  修正前の分布を「幅」ではなく「平均」で語れるようになる。
- **8ch 同時発音での CPU の山を測る。** `SYNC2.MDX` のドローンを 7 本に増やし、
  `-DSTATS_PROFILE=1` で `SVCTIME` の `mdx` と `SEQ LAG` を見る。`MDX_BUDGET_US`（500µs）を
  超えて tick が分割されるようなら、前線を寄せる操作を「1 tick に 1 回」にまとめる余地がある。
