# YM2151 の BUSY フラグと `opm_write()` の待ち時間

`opm_write()` はデータサイクルのあと `OPM_T_DATA_US`（25µs）を固定で待っている。
`r 0` / `r 1` でステータスレジスタの BUSY (bit7) が読めるようになったので、
**この固定ウェイトを BUSY のポーリングに置き換えるべきか**を実測で判断するための調査。

## 解析結果の要約

| 項目 | 結論 | 根拠 |
| --- | --- | --- |
| データ書き込みと BUSY 解除の関係 | 書き込みから **67.1 ± 0.2 φM サイクル**で BUSY が落ちる（φM=4MHz で 16.8µs / 3.579545MHz で 18.8µs） | [§1](#1-busy-の長さ--φm-を振って傾きから求める) |
| レジスタアドレスと BUSY 長の関係 | **どのレジスタでも同じ。** 12 レジスタでばらつき 16ns。8ch 発音中も同じ | [§3](#3-レジスタにもチップの状態にも依存しない) |
| アドレスサイクルと BUSY の関係 | **アドレスサイクル (A0=0) は BUSY を立てない。** `OPM_T_ADDR_US` はポーリングでは 1ns も削れない | [§4](#4-アドレスサイクルは-busy-を立てない) |
| 書き込みと BUSY アサートの関係 | BUSY が立つのは書き込みの **2.9 φM サイクル後**（φM=4MHz で 0.73µs）。即座には立たない | [§1](#1-busy-の長さ--φm-を振って傾きから求める) |
| ステータス読み出し 1 回の所要時間 | 連続ポーリングで **1.00µs**、単発の `opm_read()` で 2.00µs | [§2](#2-測定系の妥当性) |
| 待ち方と 1 レジスタ書き込みの所要時間の関係 | 固定 25µs = **32.0µs** / 固定 18µs = **25.0µs** / BUSY ポーリング = **25.0µs** | [§詳細](#待ち方ごとのベンチマーク) |
| 待ちの繰り延べと書き込みのブロック時間の関係 | 書き込みの間に 20µs 以上の仕事が挟まると **7.0µs** まで縮む。密なループでは縮まない | [§詳細](#待ち方ごとのベンチマーク) |
| MDX 再生中の `mdx_service()` の滞在時間 | 49.0ms/s → 固定 18µs で 41.8ms/s、繰り延べを足して **38.8ms/s** | [§詳細](#実再生での効果) |

## 判明した仕様

### BUSY フラグのタイミング（φM を単位とする）

```
  データサイクルの /WR 立ち上がり
    |
    |<-- 2.9 サイクル -->|                                    BUSY=1
    |                    |<--------- 64.2 サイクル --------->|
    0                   2.9                                67.1  [φM サイクル]
```

| φM | BUSY が立つ | BUSY が落ちる |
| --- | --- | --- |
| 4.000000 MHz | 0.73 µs | **16.79 µs** |
| 3.579545 MHz | 0.82 µs | **18.76 µs** |

- **BUSY 長はレジスタアドレス・書き込む値・チップの発音状態のいずれにも依存しない。**
  内部転送に固定サイクル数かかるだけと考えられる。
- **アドレスサイクル (A0=0) では BUSY は立たない。** データサイクル (A0=1) だけが立てる。
- データシート由来としてドキュメントに書かれている 68 サイクルは、実測の 67.1 ± 0.2 と
  1 サイクル以内で一致する。この測定では 67 と 68 を区別できない
  （[不明点](#不明点未解決事項)）。

### 待ち方ごとの書き込み所要時間（φM=4MHz）

| 待ち方 | 密なループ | 間に 20µs 以上の仕事があるとき |
| --- | --- | --- |
| 固定 25µs（現状） | 32.00 µs | 32.00 µs |
| 固定 18µs | 25.01 µs | 25.01 µs |
| BUSY ポーリング | 25.00 µs | 25.00 µs |
| 固定 25µs + 繰り延べ | 32.01 µs | **7.00 µs** |
| 固定 18µs + 繰り延べ | 25.01 µs | **7.00 µs** |
| BUSY ポーリング + 繰り延べ | 25.61 µs | 9.00 µs |

「繰り延べ」はデータサイクル後に待たずに戻り、次にバスを触る直前で待ちを消化する方式
（参照実装 MXDRV の `L_WRITEOPM` と同じ構造）。7.00µs は待ちを全部他の仕事に吸収させても
残る部分で、`t_WR`(1) + `t_ADDR`(5) + `t_WR`(1) にあたる。

## 結論の根拠

### 1. BUSY の長さ — φM を振って傾きから求める

ステータスの読み出しには時間がかかるので、「書き込みから d だけ待って読む」を掃引しても
得られる境界は `d = T_busy − offset` であって、`offset`（読み出しがバスをサンプルする
までの時間）が分からないと `T_busy` が出ない。

**sys_clk を 144MHz に固定したまま φM だけを 1.2〜3.6MHz で振ると、`offset` は変わらずに
`T_busy` だけが 1/φM に比例して伸びる。** 境界 `d` を 1/φM の 1 次式として最小二乗すると、
傾きが BUSY の φM サイクル数、切片が `−offset` になる。

2 回の掃引（計 12 点、[result/scale-phim.tsv](result/scale-phim.tsv) と
[result/scale-phim-run1.tsv](result/scale-phim-run1.tsv)）の結合フィット:

```
  N       = 67.14 ± 0.15 φM サイクル
  offset  = 1065 ns
  残差 RMS = 104 ns
```

立ち上がり側も同じ方法で 9 点をフィットして **2.92 サイクル**（残差 RMS 186ns）。

### 2. 測定系の妥当性

これは YM2151 の仕様ではなく、上のフィットが信用できることの確認。

- **フィットで出た `offset` 1065ns は、読み出し経路から計算した値と一致する。**
  掃引用のステータス読みは「D0-D7 を入力へ倒す → A0/`/CS` を確定 → `t_SETUP`(104ns) →
  `/RD` を L → `t_RD`(1000ns) → サンプル」なので約 1.15µs。独立に求めた 2 つの値が
  合うので、傾きの側も信用してよい。
- **ポーリング 1 回の所要時間を直接測ると 1.003µs**（[result/variants.txt](result/variants.txt)）で、
  `t_SETUP` + `t_RD` + GPIO 操作という内訳と合う。
- φM=4MHz での掃引は**遷移が 1 掃引ステップ（125ns）で切り替わり、32 回の試行で
  ばらつきがゼロ**（[result/sweep-4.000MHz.tsv](result/sweep-4.000MHz.tsv)）。φM は sys_clk の
  整数分周なので、バス操作と φM の位相関係が試行ごとに変わらないため。
  φM が 1µs（タイマの刻み）と整合しない値では位相がばらけ、遷移が数百 ns の帯になる。

初期の掃引は `opm_read()` をそのまま使っていたため、内部の `busy_wait_us_32(1)` が
タイマ境界へ丸めてサンプル時刻が 1µs 単位に量子化されていた。掃引用の読み出しだけ
サイクル基準の待ちに差し替えて分解能を回復させてある（[§解析方法](#解析方法)）。

### 3. レジスタにもチップの状態にも依存しない

代表 12 レジスタで境界を測った結果（[result/regs.tsv](result/regs.tsv)、φM=4MHz、各 32 回）:

| レジスタ | 0x01 | 0x08 | 0x0f | 0x12 | 0x14 | 0x18 | 0x1b | 0x20 | 0x28 | 0x38 | 0x60 | 0xe0 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 境界 (ns) | 15550 | 15562 | 15558 | 15558 | 15554 | 15546 | 15562 | 15550 | 15546 | 15562 | 15554 | 15562 |

**ばらつきは 16ns**（掃引ステップ 125ns より小さい）。キーオン (0x08)・タイマ (0x12)・
LFO (0x18)・TL (0x60)・RR (0xE0) のどれも同じ。

8ch を発音させた状態（全スロット AR=31 / RR=0 でキーオンし、音を出したまま）で測っても
境界は 15546ns で変わらない（[result/sweep-sounding.tsv](result/sweep-sounding.tsv)）。

**この一様性が採否の分かれ目になる。** BUSY 長が状況で変わるならポーリングでしか
追従できないが、一定なら φM から待ち時間を計算するだけで同じ結果が得られる。

### 4. アドレスサイクルは BUSY を立てない

アドレスサイクル (A0=0) だけを行って掃引すると、**0〜30µs の 241 点すべてで 32 回とも
BUSY=0**（[result/sweep-addr-cycle.tsv](result/sweep-addr-cycle.tsv)）。

`OPM_T_ADDR_US`（5µs）は BUSY とは無関係な仮置きの値なので、BUSY ポーリングを入れても
ここは 1ns も縮まない。逆に言えば、ここを詰める作業は BUSY とは独立にできる。

### 5. 書き込みが化けていないことの確認

YM2151 のレジスタは読み戻せないので、待ちを詰めた結果として書き込みが化けても直接は
見えない。**タイマ A の周期は書き込んだ CLKA そのもの**（`64 × (1024 − CLKA) / φM`）
なので、これをレジスタの読み戻しとして使う。

CLKA を 896〜1007（周期 256µs〜2048µs）で 2048 回振り、毎回 `0x10` / `0x11` / `0x14` ×2 を
書いてから周期を測り、期待値との差の最大を見る。

| 構成 | 最大誤差 |
| --- | --- |
| 現状（固定 25µs） | 22 µs |
| 固定 18µs | 10 µs |
| BUSY ポーリング | 8 µs |
| 固定 18µs + 繰り延べ | 14 µs |
| BUSY ポーリング + 繰り延べ | 20 µs |
| 固定 18µs（φM=3.579545MHz） | 13 µs |

タイマ A は 64 φM サイクル（φM=4MHz で 16µs）刻みで動くので、**測定のノイズ床が 16µs** ある。
どの構成もその範囲に収まっており、書き込みが落ちたり化けたりした形跡はない。
参考までに、待ちを異常に詰めると誤差が 1000µs 台に跳ね上がって明確に区別できる
（[§詳細](#t_data-を詰めたときの破綻点)）。

## 解析方法

### 測定の原理

BUSY をポーリングして測ると、ポーリング自身のバス操作（`/CS` と `/RD` のトグル）が
測定対象を乱す。そこで **遅延を振って 1 回だけ読む** 方式にした。

```
1 点の測定:
  100µs 待って OPM をアイドルにする
  アドレスサイクル → t_ADDR → データサイクル
  busy_wait_at_least_cycles(d)      ← d を 125ns 刻みで振る
  ステータスを 1 回だけ読んで bit7 を記録
これを 32 回（φM 掃引では 64 回）繰り返し、BUSY=1 だった回数を数える
```

境界の期待値は `E[b] = Σ P(BUSY=1 at d) × Δ` で求める（`Δ` = 125ns）。立ち上がりと
立ち下がりを分けて積算するので、位相がばらけて遷移が帯になっても平均が取れる。

掃引用のステータス読みは `opm_read()` と同じバス操作をするが、`t_RD` の待ちだけ
`busy_wait_us_32()` ではなく `busy_wait_at_least_cycles()` にしてある。
`busy_wait_us_32(1)` は 1µs のタイマ境界へ丸めるので、そのままだとサンプル時刻が
1µs 単位に量子化されて 125ns の掃引ステップが無意味になる。

### 診断コマンド

`-DOPM_DIAG=1` でのみリンクされる `busy` コマンドを一時的に足して測った。
実装は [diag.patch](diag.patch)、使い方は[付録](#付録)。**本体には残していない。**

`opm_write()` の待ち方は 2 つのビルドスイッチで切り替えられるようにした。

| スイッチ | 内容 |
| --- | --- |
| `OPM_BUSY_POLL` | 待ちの中身を固定ウェイトから BUSY ポーリングへ |
| `OPM_BUSY_DEFER` | 待つ位置を「書き込み後」から「次にバスを触る直前」へ |
| `OPM_T_DATA_US` | `opm.h` の `t_DATA` を上書き |

### 測定の限界

- **BUSY のアサートを φM=4MHz で直接は観測できない。** ステータスを最も早くサンプル
  できるのは書き込みの 1065ns 後（読み出し経路の所要時間）で、アサートの推定値
  730ns はそれより手前にある。アサート時刻は φM を下げた測定からの外挿。
- **書き込みの健全性はタイマ A 経由でしか見ていない。** 直接検証したのは
  レジスタ `0x10` / `0x11` / `0x14` だけ。分解能はタイマ A の刻み 16µs。
- 測ったのは**この 1 個体・この温度・この電源**だけ。

## 詳細な解析結果

### BUSY 消滅時刻の掃引

φM=4MHz（[result/sweep-4.000MHz.tsv](result/sweep-4.000MHz.tsv)）:

```
delay_ns  busy/32
  15375     32
  15500     32     ← 全試行で BUSY
  15625      0     ← 全試行でクリア
  15750      0
```

φM=3.579545MHz（[result/sweep-3.579MHz.tsv](result/sweep-3.579MHz.tsv)）では位相が
ばらけるので 17500〜17875ns が遷移帯になり、期待値は 17757ns。

### φM 依存性

[result/scale-phim.tsv](result/scale-phim.tsv)（sys_clk=144MHz 固定、各 64 回）:

| φM (Hz) | 立ち上がり (ns) | 立ち下がり (ns) |
| --- | --- | --- |
| 3600000 | 0 | 17630 |
| 3000000 | 248 | 21406 |
| 2400000 | 156 | 26851 |
| 1800000 | 726 | 36159 |
| 1440000 | 1078 | 45574 |
| 1200000 | 1439 | 54731 |

立ち上がり側の 3.6MHz / 3.0MHz は、アサートがサンプル可能な最速時刻より手前にあるため
0 に張り付く（打ち切られた観測なのでフィットからは除いた）。

φM=1.0MHz と 2.0MHz は**意図的に使っていない**。φM の周期がタイマの刻み 1µs の整数倍に
なると位相が固定され、試行ごとにばらけなくなって「32 回中 16 回」のような二値的な結果に
なる。最初の掃引でこれを踏んだ。

### 待ち方ごとのベンチマーク

`opm_write(0x60, 0x7f)` を 2000 回繰り返し、書き込みの間に `work_us` の空回しを挟んで
1 回あたりの時間を測った（[result/variants.txt](result/variants.txt)、φM=4MHz）。
`write_ns` は 1 回あたりから空回しぶんを引いた値。

| work_us | 現状 | 固定18µs | ポーリング | 繰り延べ | 18µs+繰り延べ | ポーリング+繰り延べ |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 32004 | 25006 | 25004 | 32005 | 25005 | 25606 |
| 2 | 32003 | 25002 | 25003 | 30000 | 23002 | 23574 |
| 5 | 32003 | 25003 | 25003 | 27000 | 20001 | 20336 |
| 10 | 32002 | 25002 | 25002 | 22000 | 15000 | 15572 |
| 15 | 32003 | 25003 | 25001 | 17000 | 10000 | 11001 |
| 20 | 32002 | 25002 | 25002 | 12001 | **7003** | 9002 |
| 30 | 32002 | 25002 | 25002 | **7003** | **7003** | 9002 |
| 50 | 32002 | 25001 | 25001 | **7002** | **7003** | 9003 |

読み取れること:

- **BUSY ポーリングと「φM から計算した固定 18µs」は同値**（25.004 と 25.006）。
  ポーリング回数の最大は 15 回で、タイムアウトは 1 度も起きていない。
- **繰り延べは、間に挟まる仕事が待ち時間を超えるまで線形に効く。** 超えたところで
  非吸収コアの 7.00µs に張り付く。
- **ポーリングは繰り延べと組むと固定ウェイトより 2µs 損をする**（9.00 対 7.00）。
  BUSY が既に明けていても、アサート遅延を踏まないための下限待ちと 1 回の読み出しを
  必ず通るため。密なループでも 25.61 対 25.01 でわずかに遅い。

### 実再生での効果

`DRACULA/dra05.mdx`（MDX ファイルのうち最も `mdx_service()` が重い曲）を再生し、
`-DSTATS_PROFILE=1` で 20 秒ぶんの統計を取った（[result/playback.txt](result/playback.txt)）。

| 構成 | `mdx` 滞在時間 | CPU | I2S 最小 | UNDERRUN / E0 / RXSTALL / OVERRUN | SEQ LAG |
| --- | --- | --- | --- | --- | --- |
| 現状 | 49026 µs/s | 40% | 854/1024 | 0 / 0 / 0 / 0 | 171 µs |
| 固定 18µs | 41788 µs/s | 40% | 872/1024 | 0 / 0 / 0 / 0 | 125 µs |
| BUSY ポーリング | 44057 µs/s | 40% | 869/1024 | 0 / 0 / 0 / 0 | 125 µs |
| 固定 18µs + 繰り延べ | 38778 µs/s | 40% | 873/1024 | 0 / 0 / 0 / 0 | 177 µs |

- 現状と固定 18µs の差 7238µs/s を 1 回あたりの短縮 7µs で割ると、**この曲は毎秒
  約 1030 回レジスタを書いている**。
- **`mdx` の滞在時間は 21% 減るが、CPU 使用率は 40% のまま変わらない。** 浮いた時間は
  メインループの空転に回るだけで、他のサービスの数字も動かない。
- **`SEQ LAG` に系統的な差は出ない。** 125〜177µs のばらつきは同じ構成でも同程度に出る。
- **ポーリングでもキャプチャ系の統計は悪化しない。** `E=0`（YM3012 の禁止コード）・
  `RXSTALL`・`OVERRUN`・I2S アンダーランはすべて 0 のまま。
  この曲の書き込みレートでは `/RD` のトグルは毎秒 15000 回ほどで、
  D0-D7 が 5V を受けている時間の割合は 1.6% にとどまる。

なお `SEQ LAG` は README §8.2 が挙げる 700µs ではなく 74〜177µs だった。手元の MDX を
一通り再生した範囲ではこの程度で、`snd_voice()`（24 書き込み = 772µs）が単独で
`MDX_BUDGET_US` を超えても、`reslip` が出るほどの遅れにはなっていない。

### `t_DATA` を詰めたときの破綻点

`t_DATA` を変えて[§5](#5-書き込みが化けていないことの確認)の検証を回した結果:

| `t_DATA` | 25 | 20 | 18 | 17 | 16 | 15 | 14 | 12 | 11 | 10 | 9 | 8 | 6 | **4** | **2** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 最大誤差 (µs) | 21 | 16 | 8 | 6 | 12 | 12 | 8 | 4 | 8 | 8 | 4 | 9 | 12 | **1092** | **1096** |

破綻するのは 4µs 以下。BUSY が明けるのは 16.8µs 後なのに 6µs でも通るのは、
**連続する 2 回のデータサイクルの間隔が `t_DATA` + 約 7µs** になるから
（データサイクルのあと次の書き込みのアドレスサイクルと `t_ADDR` が挟まる）。
6 + 7 = 13µs で、これでも BUSY 期間より短い。

**BUSY より短い間隔でも書き込みが通ることは、この個体でそう観測されたというだけで
仕様ではない。** 待ち時間を決める根拠には使えない。

### 音の突き合わせ

同じ曲を現状と「固定 18µs + 繰り延べ」で再生し、CDC #1 から 4 秒ぶんの PCM を取って
100ms ブロックごとに整列して比較した（[pcmcap.py](pcmcap.py) / [pcmcmp.py](pcmcmp.py)）。

| 比較 | 包絡線の差 | ブロックのずれ |
| --- | --- | --- |
| 現状 vs 現状（同一ビルドを 2 回） | −44.4 dB | −5〜0 サンプル |
| 現状 vs 固定18µs+繰り延べ | −31.0 dB | −70〜−45 サンプル |

**この比較では書き込みの健全性は判定できなかった。** 書き込みが速くなるとシーケンサが
早く追いつくため曲全体が約 1ms 前へずれ、そのずれ自体が残差になる。同一ビルドでも
−44.4 dB までしか一致しないので、−31.0 dB との差を「音が変わった」根拠にはできない。
書き込みの健全性は[§5](#5-書き込みが化けていないことの確認)のタイマ A による検証で見ている。

## 考察

### 選択肢

待ち方は独立した 2 つの軸に分かれる。

**軸 1: 待ちの長さ**

| 案 | 内容 | 1 write |
| --- | --- | --- |
| A | 現状（固定 25µs） | 32.0 µs |
| B | `t_DATA` を φM から実行時算出（`s_setup_cycles` と同じやり方） | 25.0 µs |
| C | BUSY をポーリング | 25.0 µs |

**軸 2: 待ちの位置**

| 案 | 内容 | 非吸収コア |
| --- | --- | --- |
| — | 現状（書き込み後にその場で待つ） | — |
| E | 次にバスを触る直前へ繰り延べる | 7.0 µs |

**軸 3: BUSY と無関係**

- D: `t_ADDR`(5µs) / `t_WR`(1µs) を詰める。合わせて 7µs あり、**案 B/C の削減幅
  7µs と同じオーダー**。今回は測っていない。

### 案 C（BUSY ポーリング）を採る理由が無い

ポーリングの唯一の理論的な利点は「BUSY 長が状況によって変わる場合の追従性」だが、
[§3](#3-レジスタにもチップの状態にも依存しない)のとおり **BUSY 長は完全に一定**だった。
その結果、実測では案 B と案 C が同値になり、繰り延べと組むと案 C のほうが 2µs 遅い。

対価は小さくない。

- **チップ不在時に無限ループする。** A0=1 の読みは OPM が居なければ直前に Pico が
  駆動した値を返すので、bit7 が立つ値を書いた直後（`opm_clear()` の `0x19`←`0x80` など）は
  永久に BUSY に見える。タイムアウトと `stats` のカウンタが必須になる。
- **アサート遅延を踏むと書き込みが黙って化ける。** BUSY が立つのは 0.73µs 後、
  最も早くサンプルできるのが 1.065µs 後で、**余裕は 0.33µs（1.3 φM サイクル）しかない**。
  `t_RD` を詰めるなど読み出しを速くする変更が、そのままこの余裕を削る。
  今回の試作では「データサイクルから最低 2µs 空けてから読み始める」で回避した。
- **D0-D7 が 5V を受ける時間が増える。** 連続書き込み時は 25µs のうち 15µs（60%）。
  実再生では 1.6% にとどまり、実測でもキャプチャ系の統計は悪化しなかった。
  ただし採用するなら README §1.3 の「A2 の個体で**読み出しを使う場合は** D0-D7 にも
  レベル変換器か分圧が要る」という条件付きの注意は**無条件**に書き換わる。
- バスの方向切り替えが毎秒 2000 回程度から増える。

**案 B なら、これらの対価をひとつも払わずに同じ 7µs が手に入る。**

### 案 E（繰り延べ）が効く場所と効かない場所

繰り延べは待ちを他の仕事に吸収させるので、**平均は下がるが最悪は下がらない**。

- 効く: サービス関数の末尾の 1 回（戻った先でメインループが `tud_task()` /
  `i2s_service()` / `capture_service()` / `pcm8_service()` を回す）、MDX の tick 処理で
  次チャンネルの MML 解釈と重なるぶん。実測で `mdx` 滞在時間がさらに 3.0ms/s 減った。
- 効かない: `opm_clear()`（87 回）・`key_off_all()`（40 回）・`snd_voice()`（24 回）の
  密なループ。ここには重ねる仕事が無いので 1 回あたり 25µs のまま。
  **I2S アンダーランと `SEQ LAG` を決めるのはこちらなので、最悪ケースは改善しない。**

新たに増える制約もある。`opm_write()` がチップの BUSY 中に戻るので、**φM を止める /
張り替える前（`clockmode.c` の分周比の張り替えは SM を一瞬止める）と `opm_reset()` の前に
未消化の待ちを消化する**必要がある。φM が止まると BUSY が明けないまま書き込みが化ける。
期限の比較は `time_us_32()` の 71.6 分のラップを跨ぐので符号付き差分で行う。

### 効果の大きさ

案 B + E で `mdx_service()` の滞在時間は 49.0 → 38.8ms/s（−21%）になる。
ただし **CPU 使用率は 40% のまま動かず、I2S の先行量にも `SEQ LAG` にも
キャプチャ系の統計にも差は出ない。** 現状でアンダーランもオーバーランも
`reslip` も 0 で、余裕が十分あるため。

つまりこれは**動いていない何かを直す変更ではなく、余裕を積み増す変更**である。

### 結論

- **案 C（BUSY ポーリング）は採るべきでない。** 効果は案 B と同じで、副作用だけが増える。
  BUSY 長が一定であることが実測で確定した以上、ポーリングの存在理由が無い。
- **案 B（`t_DATA` を φM から実行時算出）は、採るなら最も割が良い。** 副作用が無く、
  `s_setup_cycles` と同じ「クロック依存の値は実行時に算出する」という既存の方針に乗る。
  φM を下げる将来のプリセットに対しても、固定 25µs より正しく追従する。
  値は `ceil(68 / φM[MHz]) + 1` 程度（4MHz で 18µs、3.579545MHz で 20µs）。
- **案 E（繰り延べ）は効果に対して制約が多い。** 平均しか下がらず、最悪ケースは変わらず、
  φM 切り替えと `/IC` リセットに新しい前提条件が付く。参照実装と構造が揃うという
  副次的な利点はある。
- **案 D（`t_ADDR` / `t_WR` を詰める）は未調査だが、案 B と同じオーダーの削減幅がある。**
  詰めるなら先にこちらを測るべき。今回の掃引と検証の枠組みがそのまま使える。
- どれも**現状で困っている症状を解消するものではない**。

## 不明点・未解決事項

- **BUSY が 67 サイクルなのか 68 サイクルなのか決着していない。** フィットの統計誤差は
  ±0.15 サイクルだが残差 RMS が 104ns（0.37 サイクル相当）あり、系統誤差が残っている。
  読み出しオフセットの推定と分離できていない。
- **BUSY のアサート遅延 2.92 サイクルは外挿値。** φM=4MHz では読み出しが間に合わず
  直接観測できていない。残差 RMS も 186ns と大きく、有効な点が 9 個しかない。
- **1 個体しか測っていない。** BUSY 長の個体差・ロット差・温度依存・電源電圧依存は未確認。
  README §1.3 が入力 H レベルについて書いているのと同じ不確かさがここにもある。
- **書き込みの健全性を直接検証したのはレジスタ `0x10` / `0x11` / `0x14` だけ。**
  BUSY 長がレジスタに依存しないことから他のレジスタも同じと考えられるが、
  「BUSY が明けていれば書き込みは確定している」ことそのものは検証していない。
- **`t_ADDR` と `t_WR` の最小値は測っていない。** 今回の対象外。
- **音による回帰確認ができていない。** 書き込みが速くなると曲全体が前へずれるため、
  波形の突き合わせがずれに埋もれる。

## 今後の課題

- **67 と 68 を区別する。** 読み出しオフセットを独立に決めれば分離できる。
  診断コード内で GPIO を 1 本トグルして「データサイクルの `/WR` 立ち上がり」と
  「ステータスをサンプルした瞬間」を出し、ロジックアナライザで直接測る。
  あるいは φM をさらに下げて（0.6MHz など）てこ比を倍にする。ただし YM2151 の
  下限クロックを外れるので、その領域で BUSY の線形性が保たれるかの確認が要る。
- **アサート遅延を φM=4MHz で直接観測する。** 掃引用のステータス読みから `t_RD` を
  削り（サイクル基準で 200ns 程度まで）、サンプル時刻を 0.3µs 前へずらす。
  読み出しが成立する最小の `t_RD` を先に掃引で決める必要がある。
- **`t_ADDR` / `t_WR` の最小値を決める。** `OPM_T_ADDR_US` / `OPM_T_WR_US` を振りながら
  [§5](#5-書き込みが化けていないことの確認) の検証を回し、誤差が跳ね上がる点を探す。
  `t_DATA` で同じことをやったときは 4µs で明確に破綻したので、同じ手順がそのまま使える。
  そのうえで、BUSY と無関係に得られる削減幅を案 B と比べる。
- **別個体で `busy scale` を回す。** BUSY 長が個体に依らないなら、φM から算出する
  案 B の前提が固まる。依存するなら案 C を採る理由が復活する。
- **書き込みの健全性の検証を全レジスタへ広げる。** タイマ A 以外に読み戻せるものが
  無いので、DAC 出力を使う（TL を振って出力レベルを測る、KC を振って周波数を測る）
  経路を作る。`test/lfo_noise/` のキャプチャ環境がそのまま使える。

## 付録

### 診断コマンド

`-DOPM_DIAG=1` でビルドしたときだけ `busy` コマンドがリンクされる。
[diag.patch](diag.patch) を当てて再コンフィグする。

```bash
git apply test/opm_busy/diag.patch
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DPICO_BOARD=pico2 -DOPM_DIAG=1
```

| サブコマンド | 内容 |
| --- | --- |
| `busy sweep [addr] [data] [max_ns]` | BUSY 消滅時刻の掃引。TSV（`delay_ns` / `busy` / `reps`）を出し、末尾に境界と期待値 |
| `busy addr [addr] [max_ns]` | アドレスサイクル (A0=0) だけで同じ掃引 |
| `busy regs` | 代表 12 レジスタの境界を総なめ |
| `busy scale` | φM を 1.2〜3.6MHz で振って境界を測る（sys_clk は動かさない）。最後に φM を戻す |
| `busy phim <hz>` | φM だけを指定値へ張り替える |
| `busy read` | `opm_read()` と `opm_read_once()` の 1 回あたりの所要時間 |
| `busy bench` | 空回しを挟みながら 1 write あたりの時間を測る |
| `busy verify [n]` | タイマ A の周期で書き込みが化けていないことを検証 |
| `busy stat` | ポーリングのタイムアウト回数と最大ポーリング回数 |

ビルドスイッチ:

| 変数 | 既定 | 内容 |
| --- | --- | --- |
| `OPM_DIAG` | 0 | `busy` コマンドをリンクする |
| `OPM_BUSY_POLL` | 0 | 待ちを BUSY ポーリングにする |
| `OPM_BUSY_DEFER` | 0 | 待ちを次のバスアクセス直前へ繰り延べる |
| `OPM_T_DATA_US` | 空 | `opm.h` の `t_DATA` を上書き |

**長い掃引の間は `tud_task()` を回さないとホストが USB を切断する。**
`diag_sweep()` が 1 点ごとに呼んでいる。

### ホスト側スクリプト

この Mac には `timeout` も pyserial も無いので、いずれも python3 標準ライブラリだけで
書いてある（`os.open` の `O_NONBLOCK` + `select`）。

| スクリプト | 内容 |
| --- | --- |
| [opmcmd.py](opmcmd.py) | CDC #0 へコマンドを送り、`OK` / `ERR` の行が出るまで読む |
| [playmeas.py](playmeas.py) | 曲を再生し、統計をリセットしてから 20 秒走らせて `s` を読む |
| [pcmcap.py](pcmcap.py) | CDC #1 から PCM を取り込む（CDC #1 を開いてから `p 1` を送る） |
| [pcmcmp.py](pcmcmp.py) | 2 本のキャプチャを 100ms ブロックごとに整列して突き合わせる |

### 再現手順

```bash
# 掃引（φM=4MHz）
python3 test/opm_busy/opmcmd.py "clock fixed" "clock 4" "busy sweep 60 7f" > sweep.tsv

# φM を振って BUSY のサイクル数を出す
python3 test/opm_busy/opmcmd.py "busy scale"

# レジスタ依存性
python3 test/opm_busy/opmcmd.py "busy regs"

# 待ち方ごとのベンチと書き込みの検証（ビルドを変えて繰り返す）
python3 test/opm_busy/opmcmd.py "busy bench" "busy verify 2048" "busy stat"

# 実再生での効果（-DSTATS_PROFILE=1 でビルドしておく）
python3 test/opm_busy/playmeas.py DRACULA/dra05.mdx
```
